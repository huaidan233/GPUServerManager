# 0.3.0-rc.3 打包时审查记录

记录日期：2026-10-13。范围为公开源码候选、依赖、安装工具、两份主手册与在线升级实现。本文随源码冻结，记录打包时已有的检查结果及边界，不替代部署者的硬件、网络与恢复验收。

**发布候选为 `0.3.0-rc.3`。rc.2 已完成发布包构建、全新应用数据库选择性导入、真实部署验收及故障迁移自动回滚演练；验收发现 GPU Xid 日志采集的发布缺项，rc.3 已完成对应代码修复和定向回归。** rc.2 全量回归作为未变代码的验证基线，rc.3 的变更由下述定向回归覆盖。本次没有执行裸机操作系统重装，没有创建或验收真实 GitHub Release 更新链路。

源码 ZIP、manifest 和校验文件冻结后，再对同一份资产进行构建、实机验收和最终依赖审计，结果记录在独立发布附件 `release-validation-0.3.0-rc.3.md`，并对应资产 SHA-256。附件不回填进本版源码包，也不据此以同版本改源码重新打包；如果验收发现必须修改源码的问题，应使用新的候选版本。本文不预先登记这些资产级检查为通过。

rc.2 额外独立审查主机执行器的 root 权限边界、Compose 实际行为、数据库备份覆盖、迁移、停写和崩溃恢复，修复以下问题：

rc.2 的实际部署验收还发现：标准 Server Agent 镜像未携带 `journalctl`，Compose 未提供宿主 journal 挂载，导致 `gpu_xid` 采集失败。rc.3 已修复镜像、挂载、安装器和健康采集逻辑，并完成定向回归；冻结资产的实机结果另记于上述发布附件。管理员角色不自动免除个人配额，需要在「系统 → 超级用户」单独勾选，已同步写入主手册。

Xid 修复通过标准镜像提供日志工具，只读挂载安装器探测到的宿主 journal，并显式匹配宿主当前启动周期和内核日志。采集器先验证日志可读，再区分“最近 10 分钟无匹配”与 `collector_unavailable` 降级状态；安装器不创建 journal 目录或改变宿主日志持久化策略。代码回归与冻结资产的实机验收分开记录。

## 公开发布与更新机制

- 最终候选目标为 `0.3.0-rc.3`，Python 元数据为 `0.3.0rc3`；应标记为 GitHub Pre-release。此前 rc.1/rc.2 结果按版本保留，不冒充 rc.3 最终结果。
- 移除内部部署/验收/交接资料，地址改为文档示例；保留示例配置，不携带运行数据、秘密或代理节点。
- 私有开发历史不作为首次公开历史。使用审查后的源码快照建立独立公开候选仓库，原历史留在私有工作区。
- 发布构建器扫描跟踪文件，拒绝脏树、运行数据、明显凭据、异常路径和覆盖发布资产；产生源码 ZIP、manifest、SHA256SUMS。
- GitHub 发布工作流先执行软件测试、构建、依赖审计和公开源扫描，再上传资产；本次本地审查没有创建 GitHub Release，也没有执行托管 Actions。
- 管理员可检查公开 GitHub Release；默认不配置仓库，稳定版与预发布通道分开，错误不伪装成“已是最新”。
- 原 `gsm-update check/stage` 仍只检查和暂存。rc.2 的主机升级器独立执行准备、预构建、维护排空、停服、迁移前快照、离线迁移、健康检查与失败回退；API/Web 重启不清除主机事务状态。
- 升级器的 socket 和维护标记位于 root 控制的 `<app-root>/updates-public`，只读挂入 API；应用启动在部署锁内检查执行器和恢复状态。恢复未完成时保持维护，不宣称安装成功。
- 准备记录有效 1 小时。同版本同哈希复用缓存，同版本不同内容拒绝覆盖；修改源码重新发布必须使用新版本号。
- 远程升级需要真实公开 GitHub 仓库及版本匹配的源码 ZIP、manifest 和校验文件。默认仓库为空，本地 root 暂存或模拟 GitHub 响应不代表远程发布链路已验收。
- 升级事务快照不是网页备份服务的加密归档，也不属于最新 10 份清理规则；源码缓存、事务和旧镜像引用目前没有自动过期清理策略。
- SHA-256 是一致性校验，不是独立发布签名。来源信任依赖仓库发布权限或 root 显式本地导入。

### 实机故障迁移回滚证据

在授权主机通过 root 显式导入私有故障测试包。迁移先写入并提交测试表，再以失败状态退出，随后主机执行器自动执行回退。该故障包不作为公开发布资产。

- 控制服务恢复到升级前记录的精确 Docker 镜像 ID。
- 迁移写入的测试表在恢复后不存在，控制数据库完整性检查通过。
- 演练前后的成员与容器管理记录一致，加密模型配置的存储内容哈希一致；未在记录中暴露密钥或哈希值。
- 保留的研究容器，其 Docker 标识、镜像、挂载、SSH 绑定和原状态均保持不变。

这些结果验证了“数据库已经发生写入后，失败仍能恢复”的路径。它们不代表真实 GitHub 发布链路或长期运行已经验收。

### 发布包构建、全新应用数据库选择性导入与真实部署验收

在已有授权主机上构建并部署发布包，重新建立控制、遥测和分析数据库，将原数据库、日志与状态移入 root 私有离线保存位置。按授权范围只导入需保留的研究容器及关联 SSH 配置、新管理员认证材料、加密模型设置与镜像策略。新库起始时不含旧会话、绑定和历史记录；随后验证密码、MFA 恢复码、模型配置与 SSH 可用。

这是**全新应用数据库的选择性导入**，不是保留全部历史记录的升级，也不是裸机重装。该重建操作属于本次部署验收安排，不是普通在线升级自动执行的步骤。

已完成的实机检查如下：

- 在实际 GPU 环境运行 PyTorch CUDA 与 sklearn 代码。
- 使用容器独立 SSH 密码连接；通过 SFTP 上传后从网页读取并重命名文件。
- 经对外 HTTPS 应用入口访问独立来源的 JupyterLab，验证打开票据不能重复使用，并实际连接 WebSocket 内核。
- 创建加密控制面备份，完成校验及隔离恢复演练。

验收同时暴露了上述 GPU Xid 采集缺项，因此没有将 rc.2 记为无遗漏的最终发布。公开记录不包含真实容器名称或 ID、IP、账号数量、凭据和生产路径。

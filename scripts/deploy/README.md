# One-Click Ubuntu Deployment

For the 0.3.0 prerelease, start with the consolidated Chinese
[deployment and feature guide](../../docs/deployment-guide.md) and
[user guide](../../docs/user-guide.md). This document retains script-level
operational detail; optional integrations require their own setup and acceptance.

## Isolated test deployment

Use the real GPU host with production authentication before opening a public
entry point. The test installer uses `/opt/gpu-server-manager-test`,
`/etc/gpu-server-manager-test`, `/var/lib/gpu-server-manager-test`, and the
Compose project `gsm-test`. Its workload storage is `/data/gsm-test` and
`/scratch/gsm-test`. Secrets, SSH CA, databases and operation receipts are
generated independently. Never copy test secrets or databases into production.

```bash
sudo env GSM_ALLOWED_ORIGINS=https://gpu-test.example.com \
  GSM_DOCKER_REGISTRY_MIRRORS=https://docker.m.daocloud.io \
  bash scripts/deploy/install_test_ubuntu.sh prepare
sudo bash scripts/deploy/install_test_ubuntu.sh bootstrap
sudo bash scripts/deploy/install_test_ubuntu.sh start
```

`prepare` detects host capacity, preserves existing inventory and secrets,
builds the images and checks GPU/SSH image operation. `bootstrap` creates the
first test administrator through the same interactive password and MFA flow as
production. `start` verifies an administrator exists and starts `gsm-test.service`.
It runs infrastructure checks; this is not a completed production acceptance.
Test Web/API listen on localhost ports 13000/18000, and workload SSH uses
23001–23999 bound to localhost. Access these through administrator SSH forwarding.
The agent only lists or operates containers labeled `gsm.deployment=test`;
unlabeled legacy containers remain in the production namespace. Both deployments
still share physical GPUs and host resources: do not allocate the same GPUs from
two independent schedulers. This separation is not a security sandbox for a
compromised Docker agent.

The bundled SSH image declares UID/GID 10000. The agent creates only missing
member workspace/scratch directories for an explicitly trusted image and gives
those new directories to that identity; existing data ownership is preserved.
Read-only dataset/model directories must already exist. Custom trusted SSH
images must declare `gsm.ssh.uid` and `gsm.ssh.gid` for automatic workspace
initialization. SSH host keys are generated on first container startup, so
separate containers do not share host private keys from the image.

HTTPS can be tested before an A record or public tunnel exists. Obtain a real
certificate using DNS-01 validation and keep Certbot's configuration under
`/etc/gpu-server-manager-test/acme`. After the TXT challenge succeeds:

```bash
sudo bash scripts/deploy/install_test_ubuntu.sh https
```

The optional Caddy service serves Web/BFF at localhost:14443, with trusted proxy
headers and normal certificate verification. Forward a local port to this port
and resolve the chosen domain locally when testing in a browser. For a command
line check on the server, `curl --connect-to gpu-test.example.com:443:127.0.0.1:14443
https://gpu-test.example.com/` verifies the hostname and certificate without a
public A record. Manual DNS validation does not provide unattended renewal;
configure restricted DNS automation or the final tunnel's managed certificates
before general use. Pin `GSM_HTTPS_IMAGE` to the reviewed image digest for a
reproducible deployment.

Finish HTTPS login/MFA, session and member permissions, GPU lifecycle, SSH
certificate, browser terminal, restart persistence and backup/restore checks
before production cutover. WeChat needs its actual adapter and paired route;
physical printing needs its Windows agent and printer. Infrastructure smoke
does not attest to either integration. Manage only the test stack with
`systemctl restart gsm-test.service` and the test Compose/env paths above;
the production backup/restore shell wrappers still target `gsm.service`.

## Campus workload SSH and account setup

Teachers are staff accounts with advanced compute permissions and scoped teaching
permissions; they have no academic programme or automatic graduation expiry.
New member invitations return an initial password. The member's first session
can only complete password setup; administrators also enroll their own MFA.
WeChat pairing is generated by the signed-in member from their account page.

For direct campus SSH, set `GSM_PUBLIC_SSH_HOST` in the API environment and
`GSM_AGENT_SSH_BIND_ADDRESS` in the Server Agent environment to the host's campus
IPv4 address. Keep the same values in the main deployment environment. Container
owners set an independent password from **Connections and storage**; short-lived
SSH certificates remain available. Passwords are hashed inside the container,
never stored as plaintext in the database or Docker environment. Disabling a
member revokes new password logins; it does not terminate an existing SSH session.

Docker-published ports require Docker firewall rules. The optional test service
`systemd/gsm-test-campus-ssh.service` applies `campus_ssh_firewall.py` after Docker
starts. Create `/etc/gpu-server-manager-test/campus-ssh.env` (mode 0600) with
`GSM_CAMPUS_SSH_HOST`, comma-separated `GSM_CAMPUS_SSH_CIDRS`, and
`GSM_CAMPUS_SSH_PORT_START`/`GSM_CAMPUS_SSH_PORT_END` (test defaults 23001/23999).
Install and enable the service, and add `Requires=` and `After=` for it to the
test stack's systemd unit. This IPv4 iptables helper modifies only its own chain
and filters the configured original destination and workload port range in
`DOCKER-USER`. Use explicit IPv4 binding; assess IPv6 separately before enabling it.

Existing containers retain their previous port bindings until they are stopped
and saved through **Configuration**. CPU/memory-only changes use Docker update.
GPU or SSH binding changes snapshot the writable filesystem and recreate a
stopped container, preserving mounts, port numbers, SSH settings and host keys.
The agent keeps private operation receipts and snapshot trust records in its
persistent state directory. Include this directory in backups. The changed
container must be started explicitly. If a request is interrupted, refresh and
retry the same settings so the saved operation can be reconciled.

## Network Topology

The server may remain entirely on a private LAN; a public IP is not required.
For this lab, expose the HTTPS panel through an outbound tunnel while allowing
host/container SSH only from the actual lab LAN. Do not publish SSH/TCP routes
or grant remote VPN clients direct SSH access. Container management and the
browser terminal remain available through the public panel under existing
authentication, ownership, role, and CSRF checks; do not add a public-terminal block.
Bind container SSH explicitly with `GSM_AGENT_SSH_BIND_ADDRESS`, restrict it using
the actual Docker firewall backend, and verify the permitted campus source ranges.
These are deployment requirements, not policies already applied by the installer.
Production Web access should still use HTTPS because the panel carries login
credentials, session cookies, CSRF data, terminal traffic, and SSH certificate
requests. For an internal-only deployment, use an internal DNS name with Caddy
`tls internal` or an organization CA. For cross-site access, use a private
overlay network or an outbound HTTPS tunnel. See
[`docs/deployment-topologies.md`](../../docs/deployment-topologies.md) for the
trade-offs and examples.

For this topology, point the tunnel at the controlled local proxy on
`http://127.0.0.1:3001`, which supplies trusted edge headers before forwarding
all panel routes to Web on `127.0.0.1:3000`. The local hop can be HTTP, but the
browser-facing URL must be HTTPS. Set `GSM_ALLOWED_ORIGINS` to that exact
browser-facing HTTPS origin. Do not point a tunnel at Central API port 8000 or
an Agent port, and do not publish a plain HTTP URL as a shortcut. The current
installer intentionally rejects plain HTTP production origins.

Put an HTTPS reverse proxy in front of the service, then run on a clean Ubuntu
Server with its exact public origin:

```bash
sudo env GSM_ALLOWED_ORIGINS=https://gsm.example.edu \
  bash scripts/deploy/install_ubuntu.sh
```

The bare `sudo bash scripts/deploy/install_ubuntu.sh` form is rejected unless a
trusted HTTPS origin is already present in the existing mode-0600 environment
file. Wildcards and plain HTTP origins are not accepted in production. Compose
binds Web and API to `127.0.0.1`; terminate TLS in Caddy, nginx, or another
reverse proxy and forward only the intended public routes.

## HTTPS Reverse Proxy

Only Web/BFF should receive public application traffic. Do not expose port 8000,
Server Agent, WeChat Agent, or Test Agent to the Internet. The proxy must
**replace**, not append to, the edge source headers and must authenticate them
with `GSM_EDGE_PROXY_SECRET`; the BFF otherwise collapses the request to the
single `untrusted-direct` source instead of trusting browser-supplied IP headers.
The BFF then creates a separate short-lived signature for Central API login rate
limiting.

For Caddy, load the Web environment into the service without printing the
secret to the terminal:

```ini
# sudo systemctl edit caddy
[Service]
EnvironmentFile=/etc/gpu-server-manager/web.env
```

Minimal Caddy example:

```caddyfile
gsm.example.edu {
    request_body {
        max_size 102MB
    }
    reverse_proxy 127.0.0.1:3000 {
        header_up X-GSM-Edge-Client-Source {remote_host}
        header_up X-GSM-Edge-Secret {$GSM_EDGE_PROXY_SECRET}
        header_up X-Forwarded-Proto https
        header_up -X-GSM-Client-Source
        header_up -X-GSM-Client-Timestamp
        header_up -X-GSM-Client-Signature
    }
}
```

Run `sudo systemctl daemon-reload && sudo systemctl restart caddy` after adding
the drop-in. Caddy overwrites both `X-GSM-Edge-*` headers even if the browser
sent values with the same names.

Equivalent nginx example:

```bash
sudo sh -c 'umask 077; awk -F= '\''/^GSM_EDGE_PROXY_SECRET=/{print "proxy_set_header X-GSM-Edge-Secret \"" $2 "\";"}'\'' /etc/gpu-server-manager/web.env > /etc/nginx/snippets/gsm-edge-secret.conf'
```

```nginx
server {
    listen 443 ssl http2;
    server_name gsm.example.edu;

    # Configure ssl_certificate and ssl_certificate_key for this host.
    location / {
        client_max_body_size 102m;
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-GSM-Edge-Client-Source $remote_addr;
        include /etc/nginx/snippets/gsm-edge-secret.conf;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-GSM-Client-Source "";
        proxy_set_header X-GSM-Client-Timestamp "";
        proxy_set_header X-GSM-Client-Signature "";
    }
}
```

## GPU Monitoring Runtime

The installer records `GSM_AGENT_CONTAINER_RUNTIME=nvidia` in the root-only
`gsm.env` after configuring NVIDIA Container Toolkit. Server Agent uses that
runtime with `NVIDIA_VISIBLE_DEVICES=all` and the `utility` driver capability
to run `nvidia-smi` inside its own container. Mounting the Docker socket alone
does not make host GPU telemetry available. Hosts without `nvidia-smi` retain
the `runc` runtime and can start without NVIDIA Container Toolkit.

Always load the same interpolation environment for manual Compose commands,
as the installer and systemd unit do:

```bash
sudo docker compose -f /opt/gpu-server-manager/docker-compose.yml \
  --env-file /etc/gpu-server-manager/gsm.env exec server-agent nvidia-smi
```

On a GPU host, compare the visible GPU count and UUIDs with host `nvidia-smi`
before admitting members. On a CPU-only host this command is expected to be
unavailable; Web/API health checks must still pass. After changing the runtime
or upgrading an existing systemd unit, run `sudo systemctl daemon-reload` and
`sudo systemctl restart gsm.service`.

### First Host Initialization

The installer probes the **host before installing packages or starting Docker**
and creates `/etc/gpu-server-manager/inventory/server.json`. No source changes
are needed to deploy on a machine with a different GPU count or RAM capacity.
The probe uses only Python's standard library, `findmnt`, `/proc`, PCI sysfs,
and `nvidia-smi`. Preview it without changing the server:

```bash
python3 scripts/deploy/initialize_host.py --probe
```

The inventory records the hostname, logical CPU count, usable physical memory,
GPU indices/UUIDs/models/VRAM, and filesystems backing `/`, `/data`, and `/scratch`.
Missing storage directories are reported with the filesystem they would use;
the probe never formats a disk, changes a mount, or alters the network.
An NVIDIA PCI device without a working driver is an error, not a CPU-only host.

By default, initialization reserves two logical CPUs (leaving at least one) and
10% of whole-GiB memory rounded up, with a minimum memory reserve of 2 GiB.
At least 1 GiB must remain for containers. A machine with 64 logical CPUs and
62.47 GiB RAM therefore exposes limits of 62 CPUs and 55 GiB. Override first-install
defaults with `GSM_RESERVED_CPUS` and `GSM_RESERVED_MEMORY_GB`, for example:

```bash
sudo env GSM_ALLOWED_ORIGINS=https://gsm.example.edu \
  GSM_RESERVED_CPUS=2 GSM_RESERVED_MEMORY_GB=8 \
  bash scripts/deploy/install_ubuntu.sh
```

Central API reads this file through a read-only directory mount. Production
startup refuses missing, malformed, or unsupported inventory instead of using
the development fixture. Server listings, resource presets, GPU index validation,
and CPU/memory checks when creating containers all use the saved configuration.
Approvals are checked again when executed. Presets are capped to fit the host;
CPU-only hosts advertise no GPU presets. These limits are per container; they
do not implement aggregate reservations across simultaneous containers or
workloads launched outside GSM.

Repeated installation preserves the saved inventory and reserve settings.
If the detected CPU count, memory capacity, or GPU index-to-UUID mapping changes,
the installer stops before package installation and reports the difference.
After investigating a hardware change, or to deliberately adjust reserves:

```bash
sudo python3 scripts/deploy/initialize_host.py --check
sudo python3 scripts/deploy/initialize_host.py --refresh --reserve-memory-gb 8
```

`--check` does not write. `--refresh` retains the server name and existing
reserves unless explicitly overridden, saves a timestamped `.bak`, then
atomically replaces the inventory. Run the installer again after refreshing
to synchronize the Agent's expected GPU count and restart the services.
Do not refresh a reduced inventory until existing workloads have been reviewed.
Neither detection nor refresh stops or deletes any workload.

From the first background health cycle after API startup, the Agent reports
observed CPU, memory, and GPU identities; drift opens administrator health
events without silently replacing the saved baseline. Collection failures
remain unavailable observations. An unavailable GPU observation never becomes
the development mock board. Storage observations in the initialization file
are an installation snapshot; runtime filesystem health is monitored separately.

The deployment still manages one server, with stable id `server1`; this is not
automatic registration of additional servers. HTTPS origin, SSH allowlisted
networks, certificates/tunnel credentials and administrator identity still need
deployment-specific input. Hardware detection does not infer those policies.

The inventory contains hardware metadata, not secrets. Preserve a separate copy
of the inventory and custom reserves: it is not included in the current
control-plane archive. On a replacement host, initialize and review that host's
inventory before restoring the control database; never copy the old hardware
capacity blindly. Upgrading an existing installation now requires running the
installer once to create and mount inventory before starting the new API.

The NVIDIA Container Toolkit repository defaults to the official
`https://nvidia.github.io/libnvidia-container`; the previous TUNA path returned
404 during deployment checks. `GSM_NVIDIA_CONTAINER_TOOLKIT_REPO` still overrides it.

## Request And Parser Limits

The BFF separately caps JSON bodies at 1 MiB by default and rejects requests
without a valid `Content-Length` in production. Print multipart requests allow
the configured 100 MiB file limit plus 1 MiB of envelope overhead. Keep the
ingress limit aligned when changing these values.

Central API spools each print upload before normalization. PDF and Pillow image
decoding then run in a dedicated spawned process, including print attachments
relayed by WeChat Agent; the bounded request thread performs only upload I/O and
waits for that process. The defaults and accepted ranges are 30 seconds / 1-120
seconds (`GSM_PRINT_NORMALIZE_TIMEOUT_SECONDS`), 512 MiB / 128-2048 MiB
(`GSM_PRINT_NORMALIZE_MEMORY_MB`), and 20 CPU seconds / 1-120 CPU seconds
(`GSM_PRINT_NORMALIZE_CPU_SECONDS`). Linux enforces both process resource limits,
and `GSM_PRINT_MAX_FILE_BYTES` / `GSM_PRINT_MAX_PAGES` are enforced again inside
the parser child. The parent terminates a worker that exceeds the wall-clock
deadline on every platform. WeChat attachment uploads use
`GSM_WECHAT_PRINT_UPLOAD_TIMEOUT_SECONDS=150`, independently of ordinary API
requests, so the client timeout remains longer than the maximum parser budget.
platform. Values outside these ranges prevent the print service from starting
instead of silently disabling isolation.

The installer generates `GSM_TRUSTED_PROXY_SECRET` for `api.env` and `web.env`,
and a distinct `GSM_EDGE_PROXY_SECRET` for the reverse proxy and `web.env`.
Central API verifies signatures made by the BFF. Never put either value in
browser-visible variables or any Agent environment, and never route the public
proxy directly to Central API as a workaround.

The installer writes runtime files under `/opt/gpu-server-manager`, configuration under
`/etc/gpu-server-manager`, and persistent data under `/var/lib/gpu-server-manager`.
Run it from a cloned checkout. The script copies the repository into
`/opt/gpu-server-manager/source`, then Docker Compose builds the API, Web,
Server Agent, WeChat Agent, and Test Agent images locally. Test Agent is assigned
to the Compose `smoke` profile: it is available for installer black-box checks
but is not started as a persistent production service. To run it manually:

```bash
sudo docker compose -f /opt/gpu-server-manager/docker-compose.yml \
  --env-file /etc/gpu-server-manager/gsm.env --profile smoke run --rm test-agent smoke
```

The API, Web and WeChat Agent images use fixed non-root service users. The
installer assigns persistent state and SSH CA files to the API UID/GID 10001
with owner-only permissions. Server Agent remains root because it owns the
Docker socket and host storage boundary; never expose its port or share its
socket mount with another service.
The generated production env sets `GSM_AGENT_MODE=docker`, mounts
`/var/run/docker.sock` into the Server Agent, and limits host mounts to
`/data` and `/scratch`. Stop and delete operation receipts are kept in the
root-owned SQLite database at
`/var/lib/gpu-server-manager/server-agent/operation-receipts.sqlite3`; keep this
directory mounted when replacing or restarting the Server Agent container.

### Dangerous-operation receipts and reconciliation

Central creates a stable operation ID before executing a confirmed container
stop or delete and sends it as `X-GSM-Operation-ID`. Before calling Docker, the
Server Agent atomically binds that ID to the action and target in the receipt
database. A completed receipt is replayed without invoking Docker again; reuse
for a different action or target is rejected. An `in_progress` receipt left by
a crash remains `inconclusive` and is never reclaimed for automatic execution.
Do not delete the database to clear a stuck operation, because doing so removes
the idempotency record that prevents a duplicate side effect.

The control-plane backup command does not include this node-local receipt
database. Protect it with the host backup policy, preserve its root ownership
and mode 0600, and restore it together with the matching Server Agent node. Do
not copy one node's database onto another node or roll it back independently of
the node state. After an upgrade or container replacement, verify the mount and
database before allowing stop/delete operations:

```bash
sudo test -f /var/lib/gpu-server-manager/server-agent/operation-receipts.sqlite3
sudo stat -c '%U:%G %a %n' \
  /var/lib/gpu-server-manager/server-agent/operation-receipts.sqlite3
```

If Central loses a trustworthy result, the confirmation enters
`execution_unknown` and is not retried automatically. An administrator must use
the execution reconciliation view to inspect bounded evidence. For new stop and
delete confirmations, Central queries the historical receipt by operation ID
first and validates its action and target binding. A missing, `in_progress`, or
mismatched receipt remains inconclusive and does not fall back to the current
container state; only legacy confirmations without an operation ID use current
target evidence. GPU declarations and restore authorizations use bounded Central
state evidence. Resolving the record fetches evidence again, requires an
`executed` or `not_executed` choice that matches that evidence plus an operator
note, and uses an atomic claim before synchronizing Central's local state. It
never calls the original stop, delete, GPU declaration, or restore authorization
again. Inconclusive, conflicting, or unavailable evidence leaves the record
open.

Before cutover, `gsm-member-admin migration-preflight` inventories every legacy
container owner and durable SSH key. Any old owner or managed
`GSM_AUTHORIZED_KEYS` entry stops installation for explicit mapping and review;
the installer never guesses an owner, stops a container, or rewrites mounts.
Edit `/var/lib/gpu-server-manager/member-mapping.json`, rerun the preflight, and
execute the reviewed result before retrying the installer:

```bash
sudo docker compose -f /opt/gpu-server-manager/docker-compose.yml \
  --env-file /etc/gpu-server-manager/gsm.env run --rm api \
  gsm-member-admin migrate-legacy-members \
  --mapping-file /var/lib/gpu-server-manager/member-mapping.json \
  --preflight-file /var/lib/gpu-server-manager/member-migration-preflight.json
```

The migration changes ownership metadata only and refuses stale or ambiguous
inventory.
It then creates an Ed25519 member SSH CA under
`/etc/gpu-server-manager/ssh/member_ca`, keeps the private key mode 0600, and
passes only the trusted public key into managed SSH images.

If no active administrator exists, the installer runs interactive
`gsm-member-admin bootstrap-admin`. Record the TOTP enrollment URI and one-time
recovery codes immediately. The installer starts Compose and always runs the
basic Web/API/Agent smoke. Full Web/WeChat member identity integration is optional
and prints `SKIPPED` by default, so a fresh installation does not require an
already-paired WeChat member. After setting up the connector and pairing a test
member, run it explicitly:

```bash
sudo bash scripts/deploy/install_ubuntu.sh identity-smoke
# For the isolated test deployment:
sudo bash scripts/deploy/install_test_ubuntu.sh identity-smoke
```

Set `GSM_RUN_MEMBER_IDENTITY_SMOKE=1` on installation or test `start` to make this
integration check a required gate; failure then fails the process. It asks for
the member's username, password, current TOTP when applicable, and paired route,
or accepts ephemeral `GSM_SMOKE_MEMBER_*` inputs. These values are never written
to `/etc/gpu-server-manager/gsm.env`. A skipped check is not a passed check.

## API Keys And Secrets

The installer keeps the complete root-only deployment source at:

```bash
sudoedit /etc/gpu-server-manager/gsm.env
```

Do not mount this file into every container. The installer derives mode-0600
`api.env`, `web.env`, `server-agent.env`, `wechat-agent.env`, and
`test-agent.env`; Compose injects only the configuration each service needs.
It also creates `/etc/gpu-server-manager/agent-settings.env` and mounts it into
Central API only. It contains the distinct `GSM_SETTINGS_ENCRYPTION_KEY`; Web,
Server Agent, WeChat Agent, and Test Agent receive neither provider bootstrap
variables nor database, MFA, session, backup, or printing encryption keys.

Normally, sign in as an administrator and configure both provider slots in
`System -> Agent model configuration`. The UI returns only configured flags and
short fingerprints. Replacing or testing a slot requires recent administrator
authentication; clearing requires the exact displayed confirmation phrase.
Health shows the active slot and a bounded primary cooldown after failover.

For a first-install migration only, provider values may be supplied to the
installer process:

```env
OPENAI_API_KEY=sk-...
OPENAI_BACKUP_API_KEY=sk-backup-...
OPENAI_ENDPOINT=https://api.example.invalid/v1
OPENAI_MODEL=example-model
```

They are written only to `agent-settings.env` and imported into the encrypted
control database on the first Central API start. A stored database record always
wins on later starts, so environment changes cannot overwrite an administrator's
Web configuration. After confirming the masked fingerprints in Web, clear the
two bootstrap key values from `agent-settings.env` and restart; keep
`GSM_SETTINGS_ENCRYPTION_KEY`, endpoint, and model intact.

WeChat channel credentials are copied from the root-only configuration source
only into `wechat-agent.env`. After editing the source, rerun the installer to
refresh service-scoped files, then restart:

```bash
sudo systemctl restart gsm.service
```

Personal WeChat text direct messages can use the native Tencent iLink connector.
After updating the deployed source and Compose file, run the interactive
`setup_wechat_ilink.sh` on the server, scan the QR code, and send a fresh account
pairing code in the WeChat bot conversation. See
[`docs/wechat-ilink.md`](../../docs/wechat-ilink.md) for production/test commands,
state persistence, privacy boundaries, delivery behavior, and acceptance steps.
It uses outbound HTTPS long polling and needs no public callback. The optional
`wechat-ilink` Compose profile runs a receiver with only the inbound HMAC secret;
the shared state directory belongs to UID/GID 10001 and is mounted only into the
WeChat services. Keep one receiver replica; per-account leases also prevent two
accidentally started receivers from consuming concurrently.

`GSM_WECHAT_CHANNEL=webhook` remains the default for an existing external JSON
bridge. Official accounts and WeCom still need their own platform connectors;
the optional WeChat app credentials in `.env.example` do not implement them.
See [`docs/wechat-bot-status.md`](../../docs/wechat-bot-status.md) for supported
actions and the limits of current test evidence. The panel tunnel does not
automatically publish a WeChat callback.

An administrator or the member account workspace generates a ten-minute,
single-use pairing code. A WeChat adapter calls `POST /wechat-agent/inbound`;
the member binds the route by sending `/pair <code>`. Reissuing or unbinding a
route revokes the previous route without copying a role into the binding.

Do not put real keys in `.env.example` or commit them to the repository.
See `docs/secrets.md` for the full rule.

## Agent Access

Do not issue or distribute per-member API or Agent tokens. Member Agent actions
enter through the bound WeChat route and are attributed by Central API to that
live member. Provider credentials belong to the administrator-managed primary
and fallback configuration and must not be placed in member shells or chat
messages.

```bash
sudo env GSM_ALLOWED_ORIGINS="https://gsm.example.edu" \
  GSM_DOCKER_REGISTRY_MIRRORS="https://docker.m.daocloud.io,https://registry.cn-hangzhou.aliyuncs.com" \
  GSM_CONFIGURE_DOCKER_MIRRORS=auto \
  GSM_AGENT_MODE=docker \
  GSM_SOURCE_DIR="$PWD" \
  GSM_PYTORCH_GPU_IMAGE="pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime" \
  bash scripts/deploy/install_ubuntu.sh
```

Use `check_prereqs.sh` to inspect Ubuntu, NVIDIA GPU, Docker, Compose, and mirror settings without installing anything.

The installer starts Docker Compose and always runs the basic infrastructure
Test Agent smoke. Member identity integration runs only with the explicit gate
or `identity-smoke` command described above. The Test Agent CLI smoke path is
used by deployment; the HTTP `/test-agent/smoke` endpoint is protected by
`GSM_TEST_AGENT_TOKEN` for operators who expose it behind an internal network.

Before Compose starts, the installer also smoke-tests
`gsm/pytorch-cuda-ssh:latest` as an SSH image: it generates a temporary Ed25519
key for the isolated image-smoke path, starts the image on a localhost-only
random port, and verifies that `researcher` can SSH in and see `/workspace`.
This smoke credential is never used for member access. On GPU hosts it then runs
`gsm-pytorch-cuda-check` with `--gpus all`; CPU-only hosts clearly skip only the
CUDA execution check.

## Control-Plane Backup And Restore

Production uses three distinct SQLite files configured by `GSM_DATABASE_URL`,
`GSM_TELEMETRY_DATABASE_URL`, and `GSM_ANALYTICS_DATABASE_URL`: `control.sqlite` for the control
plane, `telemetry.sqlite` for 72-hour raw GPU evidence, and `analytics.sqlite`
for annual rollups. Only the control database and an explicit configuration
allowlist are included in backups. The installer generates the Fernet key in
`GSM_BACKUP_ENCRYPTION_KEY` with mode-0600 configuration and does not print it.

Create an online manual backup through the packaged CLI wrapper:

```bash
sudo bash scripts/deploy/backup_sqlite.sh
```

This stores a verified package under `/var/lib/gpu-server-manager/backups`.
All backup types participate in the newest-10 retention policy, including
manual, pre-upgrade and pre-restore backups. Active restore references remain
protected; unrecognized or corrupt archives are retained for manual inspection.
Restore is deliberately two-step: an administrator requests a restore in the
API, confirms the exact phrase, then runs the printed command after scheduling
an outage:

```bash
sudo bash scripts/deploy/restore_sqlite.sh <backup-key> <restore-ticket>
```

The wrapper runs `systemctl stop gsm.service`, invokes `gsm-backup restore` with
`--service-stopped`, then runs `systemctl start gsm.service` through a trap even
on failure.
It accepts no destination path and never restores telemetry or analytics.

Backup format v2 encrypts the complete control database, including member,
program, password hash, MFA, session, pairing, personal credential, and audit
tables as well as the encrypted Agent settings table. The allowlisted secret
bundle includes `GSM_SETTINGS_ENCRYPTION_KEY`, but not provider bootstrap
variables; primary and fallback provider plaintext exists only after decrypting
both the backup and the settings record. Plaintext v1 archives remain readable
for rollback. Keep an offline copy of the backup encryption key and the SSH CA
private key; neither can be recovered from the encrypted archive alone. After a
restore, verify the recovered config includes the matching settings encryption
key, start the service, log in as an administrator, check both masked provider
fingerprints, and rerun the member identity smoke before reopening the reverse
proxy.

For an application rollback, create a `pre_upgrade` backup, retain the old source
revision and image IDs, stop with `systemctl stop gsm.service`, restore the
selected backup if its schema changed, deploy the old revision, and restart with
`systemctl start gsm.service`. Never replace only the control database while the
service is running.

## Member Operations

Administrators invite members from the Web member workspace. Share the initial
password with its intended member; the first login requires a new personal password.
Administrators use TOTP for login and recent-auth commands. To recover lost MFA
locally:

```bash
sudo docker compose -f /opt/gpu-server-manager/docker-compose.yml \
  --env-file /etc/gpu-server-manager/gsm.env run --rm api \
  gsm-member-admin reset-admin-mfa --username <admin-username>
```

Store the new recovery codes immediately. The command revokes existing sessions.
Routine password changes, session revocation, and WeChat unbinding are available
from the account/member workspaces.

For bulk onboarding, upload a UTF-8 CSV in the member workspace with this exact
header:

```csv
username,display_name,member_kind,role,program_level,enrollment_year
alice,Alice Zhang,student,user,master,2026
prof-li,Professor Li,staff,teacher,,
```

Review the parsed rows before confirming. A batch contains 1 to 100 rows and is
atomic: validation or username conflicts leave the entire batch unwritten.
Initial credentials appear only after the transaction commits; record and deliver
them to the intended members. Members generate their own WeChat pairing codes
after signing in.

The default master's program runs from September 1 of the enrollment year to
July 1 three years later. A doctoral program runs to July 1 four years later.
Extensions require a reason. Master's-to-doctoral promotion closes the master's
record and preserves it in history. The member workspace previews all calculated
dates before confirmation.

On the day after expected graduation the account becomes `pending_exit` and can
stop or inspect existing containers but cannot allocate new resources. Disabling
immediately revokes Web, WeChat, and new SSH access while leaving
containers running. Containers with a member's private data mounts cannot be
transferred directly: the recipient creates a new container and explicitly
migrates only authorized project files. Resolve container ownership and data
retention before archiving a member; a metadata change must not expose the source
member's entire workspace.

## Credential Rotation

Rotate Agent, Test Agent, WeChat service, and inbound secrets one at a time in
the root-only `gsm.env`, rerun the installer to regenerate service-scoped files,
restart the affected services, and rerun smoke checks. Rotating the session hash
key intentionally signs out every Web session.
Rotating the MFA encryption key requires re-enrolling all administrator TOTP
credentials. Rotating the SSH CA requires updating the trusted public key for
managed images and invalidates certificates issued by the old CA; preserve the
old CA only for a bounded rollback window.

Rotate provider keys through the Web System workspace, one slot at a time, and
test the replacement before clearing the old slot. Do not directly rotate
`GSM_SETTINGS_ENCRYPTION_KEY`: existing provider ciphertext depends on it. A
settings-key rotation requires an explicit decrypt-and-re-encrypt migration and
a fresh verified backup.

## Windows Print Agent

Central API stores encrypted print artifacts under
`/var/lib/gpu-server-manager/print-jobs`. Drafts expire after one hour, terminal
artifacts remain available for reprint for 24 hours, and metadata is retained for
90 days. Print artifacts are excluded from control-plane backups. Cleanup failures
and Agent or printer heartbeat staleness appear as administrator health events.

Create the Windows Print Agent credential on the Central host. The token is shown
only by a successful issue or rotation command; Central stores only its hash:

```bash
sudo docker compose -f /opt/gpu-server-manager/docker-compose.yml \
  --env-file /etc/gpu-server-manager/gsm.env exec -T api \
  gsm-print-agent-admin issue windows-print-a --name "Lab Print PC"

sudo docker compose -f /opt/gpu-server-manager/docker-compose.yml \
  --env-file /etc/gpu-server-manager/gsm.env exec -T api \
  gsm-print-agent-admin rotate windows-print-a

sudo docker compose -f /opt/gpu-server-manager/docker-compose.yml \
  --env-file /etc/gpu-server-manager/gsm.env exec -T api \
  gsm-print-agent-admin revoke windows-print-a
```

On the target Windows computer, install Python, the fixed PDF renderer, and a
normal Windows printer driver. From an elevated PowerShell session run:

```powershell
.\scripts\deploy\install_print_agent_windows.ps1 `
  -CentralUrl "https://gsm.example.edu" `
  -AgentId "windows-print-a" `
  -AgentToken "<issued-once-token>" `
  -RendererPath "C:\Program Files\Lab PDF Renderer\renderer.exe"
```

The Windows Print Agent uses outbound HTTPS only; do not open an inbound Windows
firewall port. The installer uses the dedicated, non-administrator Windows virtual
account `NT SERVICE\GPU Server Manager Print Agent`, restricts
`%ProgramData%\GPU Server Manager\Print Agent`, discovers machine-visible printers,
and runs a dry-run that consumes no paper before starting the automatic service.

Use `Get-Service "GPU Server Manager Print Agent"` for service status and
`Restart-Service "GPU Server Manager Print Agent"` after an idle-time credential
rotation or software update. Keep the ProgramData directory during an update so
the dispatch journal survives. Service startup and bounded error types are written
to the Windows Application event log; they can be inspected without exposing job
content or Agent tokens:

```powershell
Get-WinEvent -LogName Application |
  Where-Object Message -Like '*GPU Server Manager Print Agent*' |
  Select-Object -First 50 TimeCreated, LevelDisplayName, Message
```

Remove the service only with the explicit gate:

```powershell
.\scripts\deploy\uninstall_print_agent_windows.ps1 -ConfirmRemoval
```

`completed` means the Windows queue reported completion, not that someone picked
up the pages. `delivery_unknown` means a submission may already have reached the
spooler; never retry it automatically. The automated Test Agent dry-run is the
software gate. Defer one-page physical printer acceptance until the target PC and
printer exist, then print exactly one non-sensitive page before general use.
